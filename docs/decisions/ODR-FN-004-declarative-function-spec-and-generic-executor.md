# ODR-FN-004: Declarative Function-Behaviour Spec and Single Generic Executor

- **Status**: accepted
- **Date**: 2026-06-19
- **Context**: <see below>
- **Decision**: <see below>
- **Consequences**: <see below>
- **Cross-repo impact**: additive widening of `FunctionMeta`; the executor is OxFunc-internal;
  the published `RegistryFunctionMeta` contract stays curated (see below).

## Context

OxFunc emulates ~507 Excel surfaces bit-exactly and must remain inspectable, maintainable,
optimizable, and **formally modelable** for decades. The constraint that dominates that
horizon is not any single function's math — it is how the library's behaviour is *represented*.

Today a function's behaviour is stated across several **parallel, hand-maintained**
dispatch representations:

1. the calc-dispatch chain (`eval_*_calc_dispatch`, e.g. `eval_shared_unary_numeric_calc_dispatch`),
2. the auto-generated by-index table (`surface_dispatch_by_index_generated.rs`, routing to each
   `eval_*_surface`),
3. the XLL scalar table (`eval_surface_q_unary_number`, the `Q`-typed add-in ABI path).

The same function's behaviour is encoded independently in more than one of these, kept in sync
by hand. That parallelism has already produced concrete drift:

- The XLL scalar table applied `EXP`/`COSH`/`SINH`/`DEGREES` with **no** non-finite guard while
  the other two paths mapped overflow to `#NUM!` — a latent shipped divergence (fixed in
  `4d90246`).
- `SIN` is intercepted by no calc-dispatch helper and rides the by-index table, while `COS`/`TAN`
  are intercepted by the calc-dispatch chain — for no principled reason, leaving their by-index
  arms dead.

`FunctionMeta` is already a **partial denotational semantics**: `determinism`,
`fec_dependency_profile` (an effect system), `coercion_lift_profile`, `kernel_signature_class`,
and now `real_result_policy` each describe one behavioural axis as a closed, named value.
`real_result_policy` / `ArgDomainGuard` (`4d90246`) is the prototype of the target shape: one
named closed-enum policy carried on the meta and read at **every** dispatch site, so the rule
cannot diverge between paths.

## Decision

Adopt a layered behaviour model governed by one invariant:

> **Each behavioural fact is declared once, declaratively, and every execution path is derived
> from that declaration** — by an interpreter at runtime or a generator at build time, never by
> a second hand-maintained copy.

### Layers

1. **Pure kernels.** The ideal math on values/`f64`, total and Excel-agnostic (`cos_kernel`,
   `factorial_of_int`, …). Unit-tested for mathematical correctness; the substrate a future
   formal model reasons about.
2. **`FunctionSpec` (grown out of `FunctionMeta`).** Every Excel deviation is a field that is a
   *closed enum or small ADT*, in the `ExcelRealPolicy`/`ArgDomainGuard` mould: argument
   preparation (per-arg coercion + reference resolution), lift/broadcast policy, the kernel
   binding, result publication (`real_result_policy`, done), error algebra, precision/rounding
   quirks, and **evidence/provenance** (the Excel build a non-default policy was verified
   against, the witness, the date). Closed enums buy exhaustiveness, enumerability, and a finite
   symbolic object a checker can ingest.
3. **One generic executor.** `execute(spec, args, ctx)`: prepare args → lift → run kernel →
   publish result → apply error algebra. This is the only behavioural code path; the three
   dispatch tables collapse into a `key → spec` lookup plus this interpreter. The
   `SIN`-vs-`COS` "which path" question disappears.
4. **Generated specializations (optimization only).** The by-index and XLL-scalar tables become
   artifacts **derived from the spec**, never hand-edited, and proven equal to the interpreter.
   The by-index table is already generated; the change is to flip the generator's input from
   hand-written arms to the spec.

### Supporting commitments

- **Quirks are a closed, named algebra with evidence.** Prefer `ArgDomainGuard::CircularTrigOverflow`
  over a bare `arg_abs_limit: Some(2^27)`: a named behaviour is a symbol you can quantify over
  and check; a magic number is not.
- **Generic property / differential tests over the spec table**, not per function: cross-surface
  equivalence (`scalar(x) ≡ array_lift([x]) ≡ xll_scalar(x)`), "every overflowing kernel declares
  a non-`PASS` `real_result_policy`", and "interpreter ≡ generated path" for all functions/inputs.
  These make the table self-policing; the drift class becomes a test failure, not a latent bug.
- **A `function_spec! { … }` macro with defaults** so a new behavioural axis is one line in the
  macro rather than a sweep over every full literal (retiring the all-literal "big-bang").
- **Export the spec table** (extending the existing registry-metadata CSV) as the inspectable,
  diff-across-Excel-releases artifact and the seed for a later formal model.

### Migration order (incremental, non-disruptive)

1. Keep widening `FunctionMeta` toward `FunctionSpec` one closed-enum axis at a time, each with a
   `DEFAULT_*` (the `real_result_policy` playbook), compiler-guarded.
2. Build `execute(spec, …)` alongside the current code and migrate the **unary-numeric family
   first** (it holds the live drift): route `SIN` and the rest through it, delete
   `eval_shared_unary_numeric_calc_dispatch`, and have the by-index generator emit calls into the
   interpreter.
3. Land the cross-surface equivalence law **before** the migration, so each move is provably
   behaviour-preserving.
4. Make the by-index/XLL generators spec-driven; delete hand-written arms as each family moves.
5. Introduce `function_spec!` and export the spec table.

W105 owns execution and gating; this record owns the model and order.

## Consequences

1. The "whole behaviour derived from one source" invariant makes the divergence class
   (scalar-table-missing-a-guard, `SIN`-on-a-different-tier) **structurally impossible** rather
   than a discipline to remember at each site.
2. `FunctionMeta`/`FunctionSpec` becomes the formal model surface and the executor its reference
   interpreter — directly serving the "inspect and formally model in future" goal.
3. Clarity and speed stop being opposed: the interpreter is the obviously-correct reference; the
   generated monomorphic paths are the optimization, equivalence-tested against it, so hot paths
   can be tuned without risking a behavioural fork.
4. Adopting a new quirk requires designing a closed enum with a default variant — a feature
   (forces explicit modelling), gated by `function_spec!` so it is one line, not a churn.
5. Cost: a generic interpreter carries indirection vs monomorphized code; mitigated by the
   generated fast paths for hot functions. The migration is reversible per family.

## Cross-repo impact

OxFml/OxCalc consume the function registry and its exported metadata
(`RegistryFunctionMeta`, the registry-metadata CSV), not the raw `FunctionMeta` literals.
Widening `FunctionMeta` is **additive** and the executor is OxFunc-internal, so neither breaks
downstream. New declarative axes are projected into the published `RegistryFunctionMeta` export
**deliberately**, not automatically — the published contract stays curated and versioned, keeping
the internal-evaluation-model / external-contract boundary intact.

This boundary is extended to the description/signature catalog by **W105-D1** (recorded in
`docs/worksets/W105_DECLARATIVE_FUNCTION_SPEC_AND_GENERIC_EXECUTOR.md`): `FunctionSpec` becomes the
single id-keyed authoring spine, signature-shape data is derived from it rather than restated in the
seed tables, and a build-time conformance check binds `SignatureSeed` / `RegistryHelpSeed` to
`FunctionMeta` so catalog drift becomes a build failure rather than silent help-text loss.
